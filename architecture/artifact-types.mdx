This page documents every artifact type in the `.gsd/` directory with examples and usage patterns.

## PROJECT.md

**Purpose:** Living document describing what the project is **right now**.

**When updated:** Slice completion when drift is detected.

**Format:**

```markdown
# Project Name

## Overview
One paragraph describing the current state of the project.

## Current Capabilities
- Feature 1
- Feature 2

## Stack
- Runtime: Node.js 20
- Framework: Express
- Database: PostgreSQL
- Auth: JWT tokens
```

**Rules:**
- Current state only (not historical)
- No roadmap or future plans (those live in ROADMAP.md)
- Updated when implementation reveals drift from documented state
- Read by agents during research and planning phases

**Parser:** None (freeform prose).

## DECISIONS.md

**Purpose:** Append-only register of architectural and pattern decisions.

**When updated:** During execution when meaningful decisions are made.

**Format:**

```markdown
# Architectural Decisions

## 2024-03-13: Authentication Strategy

Decision: Use JWT tokens with short expiry (15min access, 7d refresh).

Rationale:
- Stateless auth scales horizontally
- Short access tokens limit blast radius
- Refresh tokens stored in httpOnly cookies

Alternatives considered:
- Session-based auth (doesn't scale)
- Long-lived tokens (security risk)

Impact:
- Requires refresh token endpoint
- Requires client-side token refresh logic
- Adds complexity to logout (token revocation list)

---

## 2024-03-14: Error Handling Pattern

Decision: Structured errors with codes and context.

...
```

**Rules:**
- Append-only — never edit prior entries
- Include: date, decision, rationale, alternatives, impact
- Use `---` separator between entries
- Read during planning and research
- Append during execution (not planning)

**Parser:** None (freeform prose, date-sectioned).

## ROADMAP.md

**Purpose:** Milestone plan with slice checkboxes, risk levels, dependencies, and boundary map.

**When updated:** Written during planning, updated during reassessment.

**Format:**

```markdown
# M001: Payment Integrations

**Vision:** Add Stripe payment processing for one-time purchases and subscriptions.

**Success Criteria:**
- Users can purchase products with credit card
- Subscriptions auto-renew monthly
- Failed payments trigger notifications
- Admin dashboard shows payment history

---

## Slices

- [ ] **S01: Payment data model** `risk:low` `depends:[]`
  > After this: database schema and types exist for payments/subscriptions.

- [ ] **S02: Stripe webhook handling** `risk:medium` `depends:[S01]`
  > After this: webhook endpoint receives and verifies Stripe events.

- [x] **S03: One-time purchase flow** `risk:low` `depends:[S01,S02]`
  > After this: user can buy a product with Stripe Checkout.

- [ ] **S04: Subscription management UI** `risk:medium` `depends:[S03]`
  > After this: user can view/cancel subscriptions in account settings.

---

## Boundary Map

### S01 → S02, S03, S04
Produces:
  types.ts → Payment, Subscription, PaymentStatus (interfaces)
  db.ts    → createPayment(), getPayment(), updatePaymentStatus()

Consumes: nothing (leaf node)

### S02 → S03, S04
Produces:
  webhooks/stripe.ts → POST handler, verifyWebhook(), handleEvent()

Consumes from S01:
  db.ts → updatePaymentStatus()

### S03 → S04
Produces:
  api/purchase.ts → POST /api/purchase endpoint
  lib/stripe.ts   → createCheckoutSession()

Consumes from S01:
  db.ts → createPayment()

Consumes from S02:
  webhooks/stripe.ts → (webhook fires after checkout)

### S04 → (next milestone)
Produces:
  pages/account/subscriptions.tsx → UI component
  api/subscriptions.ts            → GET/DELETE endpoints

Consumes from S01:
  db.ts → getPayment(), Subscription type
```

**Checkbox states:**
- `- [ ]` — Not started
- `- [x]` — Complete

**Inline metadata:**
- `risk:low` | `risk:medium` | `risk:high` — Risk level
- `depends:[S01,S02]` — Slice IDs this slice requires

**Boundary map:**
- **Required section** that shows what each slice produces and consumes
- Planning artifact (not runnable code)
- Forces upfront thinking about slice boundaries
- Updated during slice planning if new interfaces emerge

**Parser:** `src/resources/extensions/gsd/files.ts:1-100` (`parseRoadmap()`)

## PLAN.md (slice-level)

**Purpose:** Task decomposition for a single slice.

**When updated:** Written during planning phase.

**Format:**

```markdown
# S01: Payment data model

**Goal:** Create database schema and TypeScript types for payments.
**Demo:** Can insert/query payment records via REPL.

## Must-Haves
- Database migrations create `payments` and `subscriptions` tables
- TypeScript interfaces exist for Payment and Subscription
- CRUD functions work (verified via tests)

## Tasks

- [ ] **T01: Database schema**
  Create migration files for payments and subscriptions tables.
  
- [ ] **T02: TypeScript types**
  Define interfaces in `src/types/payment.ts`.
  
- [x] **T03: CRUD functions**
  Implement create/read/update functions in `src/lib/db/payments.ts`.

## Files Likely Touched
- migrations/001_payments.sql
- src/types/payment.ts
- src/lib/db/payments.ts
- src/lib/db/payments.test.ts

## Verification
- Run migrations: `npm run migrate`
- Type check: `npm run typecheck`
- Tests pass: `npm test src/lib/db/payments.test.ts`

## Observability / Diagnostics
- Database query logs: `docker logs postgres`
- Type errors: `npm run typecheck`
- Test failures: `npm test -- --verbose`
```

**Sections:**
- **Goal** — What this slice achieves
- **Demo** — What the user can see/do when done
- **Must-Haves** — Observable outcomes for verification
- **Tasks** — Checkbox list of tasks
- **Files Likely Touched** — Guidance for LLM
- **Verification** — Commands to run
- **Observability / Diagnostics** — How to debug if something breaks

**Parser:** `src/resources/extensions/gsd/files.ts:100-200` (`parsePlan()`)

## PLAN.md (task-level)

**Purpose:** Individual task plan with verification criteria.

**When updated:** Written during planning phase.

**Format:**

```markdown
# T03: CRUD functions

## Goal
Implement create/read/update functions for payment records.

## Steps

1. Create `src/lib/db/payments.ts`
2. Implement `createPayment(data: PaymentInput): Promise<Payment>`
3. Implement `getPayment(id: string): Promise<Payment | null>`
4. Implement `updatePaymentStatus(id: string, status: PaymentStatus): Promise<Payment>`
5. Write tests in `src/lib/db/payments.test.ts`

## Must-Haves (Verification Criteria)

**Truths:**
- `createPayment()` returns a payment object with UUID id
- `getPayment()` returns null for non-existent IDs
- `updatePaymentStatus()` updates the status field

**Artifacts:**
- `src/lib/db/payments.ts` exists and exports 3 functions
- `src/lib/db/payments.test.ts` exists with passing tests

**Key Links:**
- payments.ts imports `Payment` type from `src/types/payment.ts`
- payments.ts imports `db` pool from `src/lib/db/connection.ts`

## Verification

```bash
npm run typecheck  # Must pass
npm test src/lib/db/payments.test.ts  # Must pass (3 tests)
node -e "require('./dist/lib/db/payments').createPayment({ amount: 100, currency: 'usd' }).then(console.log)"  # Must print payment object
```

## Context

This task implements the data access layer for payment records. It's the foundation for webhook handling (S02) and purchase flows (S03).

## Dependencies

Requires:
- `src/types/payment.ts` from T02
- `src/lib/db/connection.ts` (already exists)
```

**Must-Haves categories:**
- **Truths** — Observable behaviors
- **Artifacts** — Files that must exist with real implementation
- **Key Links** — Imports and wiring between artifacts

**Verification ladder:**
1. Static checks (typecheck, lint)
2. Command execution (build, test)
3. Behavioral testing (manual smoke test)
4. Human review (only when agent can't verify itself)

**Parser:** Freeform markdown (no structured parser).

## UAT.md

**Purpose:** User Acceptance Test script — human test instructions.

**When updated:** Written during completion phase.

**Format:**

```markdown
# S01: Payment data model — UAT

## Setup

1. Pull latest code: `git pull`
2. Run migrations: `npm run migrate`
3. Start dev server: `npm run dev`

## Test Cases

### TC1: Create Payment Record

1. Open Node REPL: `node`
2. Import functions: `const { createPayment } = require('./dist/lib/db/payments')`

4. **Expected:** Returns payment object with UUID id

### TC2: Query Payment

1. Query payment: `await getPayment('<payment_id>')`
2. **Expected:** Returns payment object with correct amount/status

### TC3: Update Payment Status

1. Update status: `await updatePaymentStatus('<payment_id>', 'succeeded')`
2. Query again: `await getPayment('<payment_id>')`
3. **Expected:** Status field is 'succeeded'

- All test cases pass
- No TypeScript errors
- Database queries execute without errors
- Payment records persist across restarts

If this slice breaks something:

```bash

npm run migrate:down
npm run dev

```

**Rules:**
- Non-blocking — user runs when convenient
- Derived from slice must-haves
- Step-by-step instructions
- Expected outcomes clearly stated

**Parser:** None (freeform prose).

## CONTEXT.md (milestone and slice)

**Purpose:** User decisions from discuss phase.

**When updated:** Written during discuss phase, updated during execution.

**Format:**

```markdown
# M001: Payment Integrations — Context

## Architecture Decisions

- Use Stripe SDK, not raw API calls
- Store payment metadata in separate `payments` table (not in `users`)
- Webhook endpoint at `/api/webhooks/stripe`
- Process webhooks async (return 200 immediately, handle in background)

## Reference Paths

- Auth middleware: `src/middleware/auth.ts`
- Error handling: `src/lib/errors.ts`
- Database types: `src/types/db.ts`
- Stripe client: `src/lib/stripe.ts` (create this)

## Constraints

- Must support both one-time and subscription payments
- Must handle webhook retries (Stripe sends multiple times)
- Must be idempotent (same event can fire multiple times)
- No external queue (process in-process for now)

## Implementation Guidance

- Use database transactions for webhook event processing
- Store raw webhook events in `webhook_events` table for debugging
- Log webhook signatures for audit trail
- Use Stripe test mode during development

## Dependencies

- `stripe` npm package (install during S01)
- Postgres extension `uuid-ossp` (already installed)
```

**Rules:**
- Written during discuss phase
- Read before implementation work
- Updated when new decisions are made during execution
- Slice-level CONTEXT.md is optional (for slice-specific decisions)

**Parser:** None (freeform prose, sectioned).

## RESEARCH.md (milestone and slice)

**Purpose:** Codebase and ecosystem research.

**When updated:** Written during research phase, frozen after planning starts.

**Format:**

```markdown
# M001: Payment Integrations — Research

## Codebase Survey

### Existing Auth
- `src/middleware/auth.ts` — JWT verification middleware
- `src/lib/jwt.ts` — Token generation and validation
- Uses `jsonwebtoken` library
- Tokens stored in `Authorization: Bearer <token>` header

### Database Schema
- `users` table has `stripe_customer_id` column (nullable)
- No `payments` or `subscriptions` tables yet
- Migration system: `db-migrate` (migrations in `migrations/`)
- Using PostgreSQL 15

### Dependencies
- `stripe` not in package.json — needs installation
- `express` 4.18.2 installed
- `pg` 8.11.0 installed (database driver)

### Error Handling Patterns
- Custom error classes in `src/lib/errors.ts`
- Global error middleware in `src/middleware/errorHandler.ts`
- Errors include `code`, `message`, `statusCode`

## Stripe Integration Patterns

### Webhook Handling
- Verify signature using `stripe.webhooks.constructEvent()`
- Return 200 immediately, process async
- Store raw event in database for replay
- Use idempotency keys to prevent duplicate processing

### Checkout Flow
- Use `stripe.checkout.sessions.create()` for hosted checkout
- Redirect user to Stripe Checkout URL
- Handle success/cancel redirects
- Wait for webhook to confirm payment

### Testing
- Use Stripe CLI for local webhook testing: `stripe listen --forward-to localhost:3000/api/webhooks/stripe`
- Test mode keys start with `sk_test_`
- Use test card numbers from Stripe docs

## Open Questions

- Should we store Stripe Customer IDs in `users` table or separate `customers` table?
  → Decision: keep in `users` table (already exists)
- How to handle failed payments?
  → Decision: webhook fires `payment_intent.failed`, update status to 'failed'
```

**Sections:**
- **Codebase Survey** — What exists, what's relevant
- **Integration Patterns** — How to integrate with external services
- **Open Questions** — Questions resolved during research

**Rules:**
- Written during research phase
- Read during planning
- Never updated after planning starts (append to DECISIONS.md instead)
- Slice-level RESEARCH.md is optional (for slice-specific deep dives)

**Parser:** None (freeform prose, sectioned).
